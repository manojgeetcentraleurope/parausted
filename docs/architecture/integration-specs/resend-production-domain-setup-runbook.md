# Resend Production Domain Setup Runbook

## Status

This runbook covers production domain or subdomain setup for Resend only. It does not approve real-recipient delivery and it does not change application behavior.

The rollout gate remains separate. Until that gate is approved, the following must remain true:

```text
RESEND_ALLOW_REAL_RECIPIENTS=false
```

## Target Sending Identity

- Provider: Resend.
- Sending subdomain: send.parausted.com.
- Recommended From: ParaUsted <giftcards@send.parausted.com>.
- Alternative From: ParaUsted <no-reply@send.parausted.com>.
- Reply-To: controlled support inbox, for example support@parausted.com.
- Purpose: transactional gift card delivery only.

## Why Use A Sending Subdomain

- It isolates transactional email reputation from the root domain.
- It makes system-generated email intent clear.
- It reduces blast radius if deliverability issues happen.
- It avoids mixing transactional gift card delivery with marketing or personal or business inbox mail.

## DNS Setup Steps

1. Open the Resend dashboard.
2. Add the production sending domain or subdomain.
3. Prefer the sending subdomain `send.parausted.com`.
4. Copy the DNS records generated by Resend.
5. Add those records at the DNS provider.
6. Expect records such as SPF or TXT, DKIM, MX or return-path, and other provider-generated records depending on the Resend dashboard.
7. Wait for DNS propagation.
8. Return to Resend and verify the DNS records.
9. Confirm the Resend domain status is verified.
10. Do not proceed to real recipients yet.

Use placeholders only when documenting or preparing the DNS changes:

```text
TYPE: TXT
HOST: <resend-provided-host>
VALUE: <resend-provided-value>
```

Additional placeholder examples may look like this:

```text
TYPE: CNAME
HOST: <resend-provided-dkim-host>
VALUE: <resend-provided-dkim-value>

TYPE: MX
HOST: <resend-provided-return-path-host>
VALUE: <resend-provided-return-path-value>
```

## DMARC Setup

Use this initial DMARC monitoring policy:

```text
v=DMARC1; p=none; rua=mailto:dmarc-reports@parausted.com;
```

- `p=none` is monitoring mode.
- `quarantine` or `reject` should come later only after authentication and delivery are confirmed.
- The DMARC report inbox must be monitored.

## Production-Like Test After DNS Verification

The first production-domain test must still use:

```text
DELIVERY_WORKER_MODE=resend
RESEND_ALLOW_REAL_RECIPIENTS=false
```

Expected result:

- The email goes only to a controlled or internal test recipient.
- `provider_response.provider = resend`.
- `provider_response.sentToTestRecipient = true`.
- `provider_response.realRecipientAllowed = false`.
- The production From address is used.

## Stop Conditions

Stop the rollout immediately if any of the following happens:

- The Resend domain is not verified.
- SPF or DKIM does not pass.
- DMARC is missing.
- The production From address does not match the verified domain or subdomain.
- A test email goes to a real buyer unexpectedly.
- `provider_response` does not record the test-recipient safety fields.
- Bounce or complaint signals appear during controlled testing.
- Any secret or API key is exposed.

## Rollback / Pause

- Keep or set `RESEND_ALLOW_REAL_RECIPIENTS=false`.
- Keep `DELIVERY_WORKER_MODE=resend` for further test-recipient-only diagnostics, or switch to `dry_run` if provider sending should pause.
- Stop scheduler or cron if one exists.
- Do not delete `delivery_events`.
- Investigate `provider_response`, `failure_reason`, and logs.
